## 1. 文件目的
本文件定義 DUPR 批次查詢工具的技術架構、功能規格、API 設計與部署方式，作為開發與測試的依據。

---

## 2. 系統架構概述

### 2.1 為什麼需要後端，而不是純前端網頁
DUPR 官方查詢端點需要登入後取得的 bearer token 才能呼叫；若把 token 或帳密放在前端 JavaScript，等於公開給所有訪客，會外洩帳號憑證。因此本工具必須是「前端 + 後端」架構，DUPR 憑證與所有對外 API 呼叫都只發生在後端。

### 2.2 建議技術棧

| 項目 | 選擇 | 原因 |
|---|---|---|
| 語言 | TypeScript | 前後端共用一種語言，型別檢查降低串接 API 時的欄位錯誤 |
| 框架 | Next.js（App Router） | 前端頁面與後端 API Route 可以放在同一個專案，不需要另外維護一個獨立後端服務；本地開發與雲端部署都方便 |
| 前端 UI | React + 內建 CSS（或 Tailwind） | 表格、進度條、CSV 上傳等元件簡單，不需要额外的 UI 框架 |
| 後端（API Route） | Next.js API Route（Node.js runtime） | 負責：登入 DUPR、批次呼叫 search/get player、彙整結果、回傳給前端 |
| 併發控制 | `p-limit`（或等效的簡單 queue） | 限制同時對 DUPR 發出的請求數（例如同時 3-5 筆），避免觸發速率限制 |
| 快取 | 記憶體快取（Map + TTL），本地開發足夠；若未來多執行個體再換 Redis | 短期內重複查詢同一人不必重打 API |
| DUPR 憑證存放 | 環境變數（`.env.local` 本地 / 平台的 Secret 本地開發與雲端都不進版本控制） | 避免帳密外洩 |

> 備選方案：也可以用 Python（FastAPI）重寫後端，直接參考社群現成的 `dupr-api-client` 套件（PyPI）省去自行摸索 DUPR 端點的時間；但因為前端仍需要一個網頁框架，會變成「兩種語言、兩個服務」，部署與維護成本較高，故本文件建議直接用 Next.js 一套搞定。若你本身較熟 Python，這是可行的替代方案，屬於架構選擇的開放問題（見第 7 節）。

### 2.3 元件與資料流

```
使用者瀏覽器
   │  1. 貼上名單 / 上傳 CSV
   ▼
Next.js 前端頁面 (React)
   │  2. POST /api/batch-lookup { entries: [...] }
   ▼
Next.js API Route（伺服器端）
   │  3. 用伺服器保存的 DUPR 帳密/Token 登入（若 token 過期則重新登入）
   │  4. 併發限流逐筆呼叫 DUPR search / get player API
   │  5. 命中快取則跳過重複呼叫
   ▼
DUPR 官方 API（events.mydupr.com / backend.mydupr.com）
   │  6. 回傳球員資料 / 分數
   ▼
Next.js API Route 彙整結果 → 回傳 JSON
   ▼
前端渲染結果表格 / 候選清單 / 匯出 CSV
```

## 3. 功能規格

### 3.1 批次輸入與查詢

#### 3.1.1 功能說明
使用者在文字框貼上多行內容（每行一筆，可為姓名或 DUPR ID），或上傳 CSV（單欄，一行一筆）；送出後前端呼叫後端批次查詢 API，並顯示進度。

#### 3.1.2 輸入 / 輸出
| 項目 | 說明 |
|---|---|
| 輸入 | 純文字（每行一筆，姓名或 DUPR ID 混合皆可）或 CSV 檔（單欄） |
| 輸出 | 每一筆輸入對應的查詢結果（見 3.2） |
| 觸發條件 | 使用者點擊「開始查詢」按鈕 |

#### 3.1.3 業務規則
1. 每行去除頭尾空白後視為一筆查詢項目，空行忽略。
2. 判斷該筆是「ID」還是「姓名」：若整行為純數字（或符合 DUPR ID 格式）則視為 ID，走 `get player`；否則視為姓名，走 `search players`。
3. 單次批次上限：⚠️ 待確認（PRD 開放問題 #3），暫定 50 筆，超過則前端提示分批查詢。
4. 併發呼叫 DUPR API 時最多同時 3-5 筆，避免觸發官方速率限制。

#### 3.1.4 API 規格
- **Endpoint**：`POST /api/batch-lookup`
- **Request**：
  ```json
  {
    "entries": ["John Doe", "1234567", "Jane Smith"]
  }
  ```
- **Response（成功）**：
  ```json
  {
    "results": [
      {
        "input": "John Doe",
        "status": "matched",
        "player": { "id": "1234567", "fullName": "John Doe", "doubles": 4.12, "singles": 3.98 },
        "candidates": null
      },
      {
        "input": "1234567",
        "status": "matched",
        "player": { "id": "1234567", "fullName": "John Doe", "doubles": 4.12, "singles": 3.98 },
        "candidates": null
      },
      {
        "input": "Jane Smith",
        "status": "multiple_candidates",
        "player": null,
        "candidates": [
          { "id": "2222222", "fullName": "Jane Smith", "location": "Taipei" },
          { "id": "3333333", "fullName": "Jane Smith", "location": "Taichung" }
        ]
      }
    ]
  }
  ```
- **Error Code**：
  | Code | 說明 |
  |---|---|
  | 400 | 輸入格式錯誤（例如空清單、超過批次上限） |
  | 401 | 伺服器持有的 DUPR 憑證失效，需要重新登入 |
  | 502 | 呼叫 DUPR API 時發生非預期錯誤（逐筆標示於該筆 status: "error"，不整批失敗） |

#### 3.1.5 驗收條件（AC）
```gherkin
Scenario: 貼上多筆姓名與 ID 混合查詢
  Given 使用者在輸入框貼上 3 行內容，其中 2 筆是姓名、1 筆是 DUPR ID
  When 使用者點擊「開始查詢」
  Then 前端顯示查詢進度
  And 查詢完成後顯示 3 筆結果，各自標示成功、查無、或待選

Scenario: 單次輸入超過批次上限
  Given 使用者貼上超過批次上限（例如 60 筆）
  When 使用者點擊「開始查詢」
  Then 系統提示「已超過單次查詢上限，請分批查詢」，不送出請求
```

### 3.2 結果表格與同名候選處理

#### 3.2.1 功能說明
以表格呈現每筆輸入的查詢結果；當姓名比對到多位候選人時，該列顯示「待選擇」狀態，使用者可展開候選清單並手動選定正確的球員。

#### 3.2.2 輸入 / 輸出
| 項目 | 說明 |
|---|---|
| 輸入 | `/api/batch-lookup` 回傳的結果陣列 |
| 輸出 | 表格 UI：輸入內容、比對球員姓名、雙打分數、單打分數、狀態 |
| 觸發條件 | 批次查詢 API 回傳後自動渲染；使用者於候選清單點選後更新該列 |

#### 3.2.3 業務規則
1. `status` 為 `matched` 時直接顯示分數。
2. `status` 為 `multiple_candidates` 時顯示「請選擇」，展開後列出候選人（含地區等輔助辨識資訊），使用者選定後該列狀態變更為 `matched`。
3. `status` 為 `not_found` 或 `error` 時以醒目樣式標示，並顯示簡短原因（查無此人 / 查詢失敗）。

#### 3.2.4 驗收條件（AC）
```gherkin
Scenario: 姓名對應多位候選人
  Given 查詢結果中某筆 status 為 multiple_candidates 且有 2 位候選人
  When 使用者展開該列並點選其中一位候選人
  Then 該列狀態變為 matched，並顯示所選候選人的分數
```

---

### 3.3 CSV 匯出

#### 3.3.1 功能說明
使用者可將目前結果表格（含已選定的候選人）匯出成 CSV 檔下載。

#### 3.3.2 輸入 / 輸出
| 項目 | 說明 |
|---|---|
| 輸入 | 目前畫面上的結果表格資料（僅前端狀態，不需要額外呼叫後端） |
| 輸出 | CSV 檔（欄位：輸入內容、比對姓名、DUPR ID、雙打分數、單打分數、狀態） |
| 觸發條件 | 使用者點擊「匯出 CSV」按鈕 |

#### 3.3.3 驗收條件（AC）
```gherkin
Scenario: 匯出查詢結果
  Given 查詢已完成且表格中有結果
  When 使用者點擊「匯出 CSV」
  Then 瀏覽器下載一份 CSV 檔，內容與畫面表格一致
```

## 4. 資料規格

### 4.1 資料模型
本工具不需要自建資料庫；查詢結果僅存在於當次瀏覽器 session（記憶體 state），伺服器端僅做短期快取（TTL，例如 24 小時）。

| 快取項目 | 說明 |
|---|---|
| Key | DUPR ID 或標準化後的姓名查詢字串 |
| Value | 球員資料（姓名、ID、雙打/單打分數、查詢時間） |
| TTL | ⚠️ 待確認，暫定 24 小時 |

若未來需要「查詢歷史紀錄」（PRD 開放問題 #4），才需要引入資料庫，目前 Out of Scope。

### 4.2 資料驗證規則
| 欄位 | 規則 | 錯誤訊息 |
|---|---|---|
| entries（輸入清單） | 非空陣列，長度 ≤ 批次上限 | 「請輸入至少一筆查詢內容」/「已超過單次查詢上限」 |
| 每筆輸入 | 去除空白後不為空字串 | （空行直接忽略，不視為錯誤） |

## 5. 例外處理

| 情境 | 處理方式 | 使用者訊息 |
|---|---|---|
| DUPR 登入 token 過期 | 後端自動嘗試重新登入一次；若仍失敗則整批回傳 401 | 「DUPR 連線異常，請稍後再試」 |
| 單筆查詢逾時 / DUPR API 錯誤 | 不影響其他筆查詢，該筆標示為 error，繼續處理其餘項目 | 該列顯示「查詢失敗」 |
| 查無此人 | 該筆標示 not_found | 該列顯示「查無此人」 |
| DUPR 回應速率限制（429 等） | 依速率限制訊息延遲重試，若重試後仍失敗才標示該筆 error | 該列顯示「查詢失敗，請稍後重試」 |

## 6. 效能與安全規格

- 回應時間要求：⚠️ 待確認（PRD KPI），暫定批次 50 筆於 60 秒內完成。
- 並發處理：對 DUPR API 的併發呼叫上限 3-5，避免觸發官方速率限制或帳號風險。
- 認證授權：
  - 本工具伺服器端保存一組 DUPR 帳號憑證（或直接保存 bearer token），存於環境變數，絕不寫入程式碼或版本控制。
  - 本工具本身不需要使用者登入（僅限個人/小範圍使用，見第 7 節開放問題）；若未來開放給多人使用，需額外設計工具自身的存取控制（例如簡單密碼保護或白名單）。
- 資料加密：所有對外呼叫走 HTTPS；DUPR 憑證於雲端部署時使用平台的加密環境變數（Secret）功能。

## 7. 部署方式：Local 還是雲端

### 7.1 建議：兩階段部署，兩者都支援

因為 Next.js 專案本身「開發模式」與「正式佈署」是同一套程式碼，這兩個階段不衝突，可以先在本機用，之後有需要再一鍵搬上雲端。

**階段一（現在）：本機（Local）**
- 指令：`npm run dev`，於 `http://localhost:3000` 使用。
- DUPR 憑證放在專案根目錄的 `.env.local`（不進 git，已在 `.gitignore` 排除）。
- 適合現況：目前只有 Charles 本人使用、資料量小、不需要對外公開，也還沒有確認 DUPR 服務條款對自動化查詢的允許範圍（PRD 開放問題 #2）。先在本機用是風險最低的做法。

**階段二（未來，若確定要開放給其他人使用）：雲端**
- 建議平台：**Vercel**（Next.js 官方推薦平台，免費方案即可）。
  - 部署方式：連接 GitHub repo，push 到指定分支即自動部署。
  - DUPR 憑證改存在 Vercel 專案的 Environment Variables（加密保存，不出現在程式碼或前端）。
  - 建議加上簡單的存取保護（例如 Vercel 的密碼保護功能，或自行加一個簡單的共用密碼頁），避免工具被公開網路上不特定人士拿去大量查詢，違反 DUPR 服務條款或造成帳號被封鎖的風險。
- 替代平台：Render、Railway 等亦可跑 Next.js，若未來需要更長時間執行的背景工作或自架資料庫，這類平台的彈性更高；但以目前需求（無資料庫、單次查詢型）Vercel 已足夠。

### 7.2 兩者比較

| | Local | 雲端（Vercel） |
|---|---|---|
| 適用情境 | 只有自己用、還在驗證 DUPR 查詢方式是否可行 | 需要讓球隊隊友/賽事主辦方等其他人也能用 |
| 成本 | 免費（僅需自己的電腦） | 免費方案可用（個人流量下） |
| 風險 | 低（不對外曝露） | 需額外做存取保護，否則等於公開讓任何人濫用 DUPR 查詢 |
| 建議時機 | 現在就可以開始開發與使用 | PRD 開放問題 #1、#2 確認後再上線 |
